## Package adapters for PyPI, RubyGems or Go modules in synchronous tasks

### ASCII transliteration and slugs (`ascii-transliteration`)

- **Proposal:** Task "titles-20-scripts": transliterate a few dozen deterministic titles of about 80 characters across 20 scripts (Latin with diacritics, Cyrillic, Greek, Arabic, Hebrew, Devanagari, CJK, Thai, and others) to ASCII. Each operation is one synchronous call per string. The check is strict: the output is pure ASCII, and a golden table covers the Latin-diacritic and Cyrillic inputs where the packages agree. For scripts where Unidecode and text-unidecode differ (for example CJK), compare only the ASCII property, or use per-package golden outputs. Packages: PyPI unidecode and text-unidecode, RubyGems babosa (transliterate/to_slug) and sixarm_ruby_unaccent (Latin accents only, so it needs a Latin-only fixture subset). If the harness gets PyPI and RubyGems support, add the npm "transliteration" and "slugify" packages and the Rust "deunicode" crate, which the brief did not list. A second variant could produce slugs.
- **Needs:** Support for PyPI and RubyGems packages as adapters of sync-operation tasks. Alternatively, a brief that includes npm, JSR or crate packages for this category.
- **Why not now:** The brief lists only PyPI (text-unidecode, unidecode) and RubyGems (babosa, sixarm_ruby_unaccent) packages. It has no npm, JSR, crates.io or Go packages. PyPI and RubyGems packages cannot be adapters of a synchronous task yet. No standard library does this job: the only builtin option is Unicode NFKD plus stripping marks, and that is a normalization form, which the brief puts out of scope. Fewer than two valid adapters are possible, so I wrote nothing and left benchmarks/ascii-transliteration/ absent.

### Chart rendering (`chart-rendering`)

- **Proposal:** Render a line chart with 10 series of 10,000 points each to SVG, using fixed dimensions, deterministic data and default styling. Check the output as an SVG string: it must be well-formed XML, contain 10 series paths, and have the expected canvas size. The size of the output SVG could be a secondary check. Packages: plotters (cargo), gonum.org/v1/plot with vgsvg (Go module), matplotlib with the SVG backend, plotly with kaleido or to_html, altair/vl-convert, and leather (PyPI). svgo is low-level SVG emission, so it would need a fair design decision about whether it counts. PNG output is less comparable because the rasterizers differ.
- **Needs:** Support for PyPI and Go module packages as adapters of a synchronous task. npm and JSR have no chart-rendering candidates in the brief; a pass could look for npm chart libraries (for example vega, chart.js with node-canvas, d3 with jsdom) that are not in the brief. Also needed is a design decision on a common output contract, such as SVG with structural checks, since each library's SVG output differs.
- **Why not now:** The brief lists no npm or JSR packages. Its packages are PyPI (matplotlib, plotly, altair, seaborn, leather, sparklines), Go modules (svgo, gonum plot) and one crate (plotters). None of the runtimes ships a standard-library chart renderer. The only usable sync-operation adapter would be plotters, so fewer than two adapters could take part. Nothing was written under benchmarks/chart-rendering/.

### Graph algorithms (`graph-algorithms`)

- **Proposal:** Task "toposort-validity": for each fixture (a DAG of a few thousand nodes with a deterministic edge list), build the graph from the edge list and return a topological order inside the measured call. The verifier checks that the order is a permutation of all nodes and that every edge goes forward, so any valid order is accepted. A second task, "scc-components", would return the strongly connected components on graphs with cycles. The verifier would compare them as a sorted partition of the nodes, so component order and node order inside a component do not matter. Packages: petgraph (toposort, tarjan_scc / kosaraju_scc), Ruby tsort (builtin, tsort and strongly_connected_components), Python graphlib (builtin, topological sort only), plus npm packages not in the brief, such as graphlib or graphology, if they are added to the brief. networkx could join once PyPI adapters exist.
- **Needs:** PyPI adapters for synchronous tasks, so networkx can take part. A category brief with npm and JSR graph packages (the current one has none). A decision on whether to build the graph inside the timed call and on the checking approach (validity check versus canonical output). A decision on how to handle the standard-library gaps, which are that Python graphlib has no SCC and JavaScript and Go have no builtin.
- **Why not now:** The brief lists no npm or JSR packages. Its only package that fits a synchronous task is the crate petgraph. networkx (PyPI) and tsort (RubyGems) cannot be adapters of a synchronous task yet. The standard libraries only partly overlap: Python graphlib has topological sort but no strongly connected components, Ruby tsort has both, and JavaScript and Go have neither. That leaves only about three uneven adapters. Topological order is also not unique, so a fair strict check needs a design decision I am not sure of. I wrote nothing under benchmarks/graph-algorithms/.

### HTML sanitizing (`html-sanitizing`)

- **Proposal:** Task "default-allowlist-fragments": sanitize about 1000 deterministic HTML fragments (scripts, on* handlers, javascript: URLs, unknown tags, SVG/iframe/style, malformed nesting) with each package's default settings. Verify properties, not exact bytes. The output must be re-parsed as safe: no script/iframe/object elements, no on* attributes, no javascript:/data: URL schemes in href or src. Benign markers (text content plus b, i, p, a[href=https], ul/li) must survive. Compare normalized visible text between packages. Participants: npm dompurify (with jsdom), the Rust crate ammonia (and possibly sanitize-html style crates), and a possible JS-side sanitize-html if it is in the brief. Later, with async/non-JS adapters: nh3, bleach, lxml-html-clean (PyPI), loofah, rails-html-sanitizer, sanitize (RubyGems), bluemonday (Go).
- **Needs:** (1) A way for an npm adapter to depend on jsdom alongside dompurify, i.e. an installed companion dependency (versions.json or the install script). (2) Confirmation that ammonia and other sanitizer crates are allowed as Rust adapters, since the brief lists no crates. (3) A decision on the property-based verifier, because sanitizer output is not byte-comparable across packages. (4) Ideally support for PyPI, RubyGems and Go-module packages in sync tasks, because most of this category lives there.
- **Why not now:** A fair, strict, synchronous task is possible in principle, but I could not make it with confidence. In the brief only dompurify is on npm. It needs a DOM implementation (jsdom) that is not in versions.json, and I may not install anything or edit shared files. The other packages (bleach, nh3, lxml-html-clean, loofah, rails-html-sanitizer, sanitize, bluemonday) are on PyPI, RubyGems or Go modules, which cannot be sync-operation adapters yet. Only a Rust crate such as ammonia could be a second adapter, and the brief does not list crates. There is also a design decision: default allow-lists and serialization differ widely between sanitizers (DOMPurify vs ammonia), so exact output comparison would fail correct packages. The check would need to be property-based, and I am not sure of that design. No files were written.

### JSON path queries (`json-path-query`)

- **Proposal:** Task name: compiled-queries. The scenario would hold a few dozen nested JSON documents of varied shape, such as catalogs, user records and event logs. Each fixture would pair a document with a fixed query. Each operation would evaluate one query against one document and return the selected values as a list. The fixtures would use only the common subset of the query languages: child access, array index, wildcard, and a simple filter or projection. The result would be a list of JSON values in document order, mapped to one common shape in every language. A query that finds nothing would return an empty list. Where a library returns null or a single value for one match, the adapter wraps it into a list, in every language alike. A first pass should use two or three separate query dialects, each with its own fixtures and checks. - JSONPath: jsonpath-rust (cargo), plus an npm package such as jsonpath-plus (to be chosen and checked against the seven-day rule). Python jsonpath-ng and Ruby jsonpath need PyPI/RubyGems support in the harness. - JMESPath: npm jmespath, PyPI jmespath, RubyGems jmespath and go-jmespath. A different query dialect, so these would be a separate task such as jmespath-queries. - JSON Pointer (RFC 6901): the Go packages go-openapi/jsonpointer and xeipuuv/gojsonpointer, PyPI jsonpointer, and npm and Rust pointer libraries. serde_json's `Value::pointer` is a built-in for Rust. This would be a separate task such as json-pointer-lookup. The checks should compare normalised lists and be strict about document order and about null versus missing. Packages run with default options as installed. Decide whether query compilation happens in `prepare` or inside the timed call. The fairest option is to prepare the compiled query once per fixture for libraries that offer it and state this in task.md, but a library with no compile step would then do all its work inside the call.
- **Needs:** 1. Support for PyPI, RubyGems and Go-module packages as adapters of sync-operation tasks. The main JSONPath and JMESPath packages are only on those registries. 2. A reviewer's choice of npm and JSR packages, since the brief lists none. Candidates are jsonpath-plus, jmespath, jsonpointer and json-p3, and each must pass the seven-day rule. 3. A decision on whether the query dialects (JSONPath, JMESPath, JSON Pointer) become one task or separate tasks. 4. A decision on whether compiling the query counts as timed work or goes in `prepare`.
- **Why not now:** A synchronous task would fit, but fewer than two adapters can be written now. The brief lists no npm or JSR packages. The only cargo crate is jsonpath-rust, and no JavaScript, Python, Ruby or Go standard library evaluates JSONPath, JMESPath or JSON Pointer. The packages that do the job (jmespath, jsonpath-ng and jsonpointer on PyPI; jmespath and jsonpath on RubyGems; go-jmespath, gjson and go-openapi/jsonpointer in Go) cannot be adapters of a synchronous task yet. I wrote nothing under benchmarks/json-path-query/ and ran no checks.

### Message translation (`message-translation`)

- **Proposal:** Build a gettext .po/.mo catalog task. Load 5,000 messages in two locales, built deterministically, then do 100,000 lookups with %s/%d-style interpolation and ngettext plural selection, using plural rules both locales share (for example en with nplurals=2 and pl or ru with 3 forms). Check each output string exactly against the expected translation. Packages: gettext-go (Go), fast_gettext and gettext (Ruby), babel.support.Translations (Python), and @moductor/libintl (JSR) if native FFI is allowed. An i18n-style key-value variant (Ruby i18n, Go universal-translator, locale-kit) would be a separate task, since its plural and interpolation models differ.
- **Needs:** Synchronous tasks for PyPI, RubyGems and Go module packages. A way to feed the same prebuilt catalog files to every adapter, in the same .po or .mo format. A decision on whether FFI-based JSR packages are allowed. No crate in the brief covers this.
- **Why not now:** The brief lists no npm or crates.io packages. Its only synchronous-capable packages are three JSR ones, and they do not share one operation. @moductor/libintl binds native gettext through FFI. @axhxrx/internationalization uses TypeScript modules as the catalog format. @locale-kit/locale-kit is a small string-fill helper. They differ in catalog format, interpolation syntax and plural model, and no standard-library builtin does the same job (Intl.PluralRules covers plurals only). The strongest packages are on PyPI (babel), RubyGems (i18n, fast_gettext, gettext) and Go modules (gettext-go, universal-translator), which cannot be adapters of a synchronous task yet. A fair task needs a design decision about a common catalog format and plural rule set. I wrote nothing under benchmarks/message-translation/.

- **Needs:** Support for PyPI and RubyGems packages as adapters of sync-operation tasks. Alternatively, a brief that includes npm and crates.io OTP packages. Separately, someone must confirm that the @hectorm/otpauth version is at least seven days old.
- **Why not now:** The brief lists only three packages: @hectorm/otpauth (JSR), pyotp (PyPI) and rotp (RubyGems). PyPI and RubyGems packages cannot be adapters of a synchronous task yet, so only one adapter is possible. One adapter is below the two-adapter minimum. I wrote nothing under benchmarks/one-time-passwords/.

### SQL parsing (`sql-parsing`)

- **Proposal:** Task "parse-statements": parse about 40 to 100 fixed SELECT, INSERT, UPDATE and CREATE TABLE statements of 100 to 2,000 characters, in memory, with one synchronous parse call per statement. The verifier needs a common result shape that all packages can be mapped to. A reasonable shape is the statement kind plus the sorted list of referenced table names and the count of top-level result columns. A strict check would also compare the number of statements. Packages: sqlparser (Rust), sqlparse, sqlglot and py-partiql-parser (Python), pg_query (Ruby), and optionally node-sql-parser or pgsql-parser (npm) if the brief is widened. Dialect differences, such as sqlparse being non-validating, need a design decision on which statements are in the shared fixture set.
- **Needs:** Synchronous task support for PyPI and RubyGems packages, which is required for sqlparse, sqlglot and pg_query. Alternatively, the brief could be widened to npm or JSR SQL parsers (for example node-sql-parser) so that at least two adapters exist. ## The file system

### Atomic file writing (`atomic-file-writing`)

- **Proposal:** Measure atomically replacing 1,000 files of 64 KiB each in a fresh temp directory, repeated 10 times. Content is deterministic per file, and the check reads every file back and compares bytes, with no leftover temp files. Packages: write-file-atomic (sync API) on npm, a builtin Node adapter (writeFileSync to a temp file, then renameSync), renameio (Go), atomos (Ruby), and builtin Python (tempfile plus os.replace), Ruby and Rust (tempfile crate persist, or std write plus rename) as baselines. Each adapter would use the same fsync policy, or the task.md would state any difference.
- **Needs:** A file-system task kind with a per-run scratch directory that is not timed and is cleaned up afterwards. The verifier would read the files back, and fsync behaviour would need a stated policy. Go-module and RubyGems adapters for non-sync tasks would also be needed, because two of the three packages are there.
- **Why not now:** Atomic file writing is file-system work (temp file, fsync, rename) and cannot be a synchronous in-memory sync-operation task. The brief's only packages are write-file-atomic (npm), atomos (RubyGems) and github.com/google/renameio (Go modules). The RubyGems and Go ones cannot be adapters of a synchronous task yet. Nothing was written under benchmarks/atomic-file-writing/.

### Directory walking (`directory-walking`)

- **Proposal:** Measure a recursive listing of every file and directory under a fixed fixture tree of about 10,000 files in nested directories. The tree would be generated deterministically once, outside the timed section, and the page cache would be warmed identically for every adapter. The result is a sorted list of relative paths. The check compares the sorted path set to the expected list, with directories and files both counted and symlinks excluded. Packages: npm readdirp, fdir, path-scurry and @nodelib/fs.walk; crates walkdir and ignore, with ignore's gitignore filtering turned off so it does the same job; builtins fs.readdirSync with recursive:true in Node, Python os.walk, Ruby Dir.glob or Find, and Go filepath.WalkDir. The PyPI package rignore and the Go modules kr/fs and godirwalk could join only once the harness supports those registries for this kind of task.
- **Needs:** A task kind that provides a pre-built on-disk fixture directory, created deterministically before measurement and passed to each adapter by path. It also needs a rule for page-cache warm-up, and file system access allowed for adapters on all runtimes. Optionally, sync-operation support for PyPI and Go module packages.
- **Why not now:** Walking a directory needs a real file system tree, which a sync-operation on in-memory inputs cannot give. Every package here (readdirp, fdir, path-scurry, @nodelib/fs.walk, walkdir, ignore, rignore, godirwalk, kr/fs) does file system I/O. The fair design questions are also open: warm versus cold cache, symlinks, ordering, and whether directories are included. I wrote no files.

### Filesystem globbing (`file-globbing`)

- **Proposal:** Build a fixed fixture directory tree of a few thousand files. It would be deterministic and have varied depth, extensions, dotfiles, node_modules-like directories and symlink-free names. Create it once, outside the measured call. Each operation expands about 10 to 20 fixed patterns against that tree: **/*.js, src/**/*.{ts,tsx}, **/test/*.spec.*, !-negations, dot-file cases and so on. The check compares the sorted lists of relative paths with an expected list, after normalising separators and the leading ./. Participants: npm glob, tinyglobby, fast-glob and globby; crates glob and globwalk; builtins fs.glob/globSync (Node 22+), Python glob.glob(recursive=True), Ruby Dir.glob and Go filepath.WalkDir with path.Match or doublestar. Exclude Go's mattn/go-zglob unless the harness supports Go modules. Defaults differ between packages (dotfiles, symlinks, ordering, absolute versus relative output), so task.md needs to pin the accepted equivalences. An unordered comparison is the likely choice.
- **Needs:** A new task kind, or a sync-operation variant, that gets a prepared fixture directory path at setup time. The harness would create the tree deterministically before timing and pass its root to each adapter. It would also need to treat file system reads as part of the measured work, with disk cache warmed or controlled, and to report file system I/O noise separately. Rust, Go, Python and Ruby adapters would need access to the same root path. Any crate used for the tree setup would have to be outside the timed region.
- **Why not now:** Filesystem globbing expands patterns by walking a real directory tree. The sync-operation task kind allows only in-memory inputs and no file system, so I wrote no files. The brief excludes in-memory pattern matching, which is the one part of this that could run in memory.

### File locking (`file-locking`)

- **Proposal:** Measure uncontended acquire then release of an exclusive lock on a lock file in a temp directory, 100,000 times in one process, checking after each cycle that the lock can be taken again. Add a second scenario with N child processes contending, where the check is that the total number of critical-section entries equals the expected count with no overlap (for example via an append-only counter file). Take part: PyPI filelock, portalocker, locket and lockfile; Go modules gofrs/flock and alexflint/go-filemutex; crate fs2; plus builtins using fcntl.flock in Python, File#flock in Ruby, syscall.Flock in Go and rustix or std File::lock in Rust. The JavaScript ecosystems have no packages in the brief, so they could be added from a wider search (proper-lockfile, lockfile) if the category is expanded.
- **Needs:** A file-system task kind with a per-run temp directory that is cleaned up. Adapter support for PyPI and Go module packages. A multi-process orchestration mode that spawns contending workers and checks a shared result. Handling of fixture state that must be reset between operations (lock file removal).
- **Why not now:** Acquiring and releasing cross-process advisory locks is a file system operation (a lock file on disk, flock/fcntl calls), and the contended variant needs child processes. That is outside the sync-operation kind. The brief lists no npm or JSR packages. Most of the listed packages are on PyPI (filelock, portalocker, locket, lockfile) or Go modules (gofrs/flock, go-filemutex), which cannot take part in a synchronous task yet. The only usable package is the crate fs2, and the only builtins would be fs-level calls. Fewer than two fair adapters exist, and in-memory inputs would not exercise the real operation. I wrote nothing under benchmarks/file-locking.

### File existence lookup (`file-lookup`)

- **Proposal:** Build a fixture directory tree in a temp directory before timing starts. It would be deep, with marker files such as package.json, .git and tsconfig.json at varying ancestor levels, plus a few directories and some misses. Each operation would start at a fixed deep path and find the nearest ancestor holding any of the candidate markers, and the verifier would compare the returned paths relative to the fixture root. Packages: find-up, escalade, locate-path, path-exists, pkg-dir and lilconfig on npm, with a Node fs builtin for comparison. Rust (the `find_up`-style crates) and Go/Python/Ruby builtins (os.Stat, pathlib, File.exist?) would use the same tree. Open design questions for the Opus pass are: sync vs async APIs (find-up and locate-path default to async, and they also offer *Sync variants); a warm-cache vs cold-cache policy; and whether to count stat syscalls. A fair comparison probably needs the fixture tree path passed to adapters, and a harness option to exclude time spent in the kernel.
- **Needs:** A harness hook that creates a deterministic fixture tree on disk before measurement, and passes its root path to adapters and to scenario.mjs. A decision on how disk I/O is measured: warm cache only, and whether kernel time counts toward CPU time. A task kind or rule that allows file system access in a synchronous task. Adapter support for the sync variants of async-first packages.
- **Why not now:** Every package in this category does its job by reading the file system (existence checks, stat calls, walking up parent directories). A sync-operation task has to run on in-memory inputs. File system work would add disk and OS cache noise, and each language's I/O path would be timed differently. The fairness of that, and how to lay out a fixture tree, is a design decision I should not make alone. The PyPI and RubyGems packages in the brief (findpython, hike) can't be adapters of a synchronous task yet. I wrote nothing under benchmarks/file-lookup/.

### File system watching (`file-watching`)

- **Proposal:** Create a directory tree of 1,000 files in a temp dir, start the watcher, apply a fixed script of 10,000 creates, writes and removes, and collect every event until a final sentinel change is seen. - **Needs:** An async or event-driven task kind with a setup phase that builds the tree and a timed phase that applies the change script and waits for quiescence. Temp-directory management, with the filesystem backend recorded (inotify vs FSEvents vs polling) and a rule for event loss and coalescing. Async adapter support in the runners. PyPI and Go module adapters for this task kind. Nice-priority control must not skew the timing of the script writer.
- **Why not now:** File watching depends on the file system, OS notification facilities (inotify/FSEvents), asynchronous event delivery, timers/debouncing and a long-lived process. None of that fits a synchronous in-memory function call per operation. The most used packages (chokidar, watchpack, watchfiles, watchdog, fsnotify, notify) are async and event-driven, and most are on PyPI or Go modules, which cannot be adapters of a sync task yet. Nothing was written under benchmarks/file-watching/.

### Retry policies (`retry-policies`)

- **Proposal:** Add an async-operation task, "fail-then-succeed". The retry policy is a fixed attempt cap with zero delay and no jitter. The result is the final value plus the attempt count, and the check requires the exact attempt count. Run it about 100,000 times per round. Packages: npm p-retry, retry, @humanwhocodes/retry; crates backoff, backon and tokio-retry (tokio-retry needs a tokio runtime); PyPI tenacity, backoff and retrying; RubyGems retriable; Go modules cenkalti/backoff (jpillora/backoff has no retry loop). The Python, Ruby and Go packages cannot be adapters of a sync task yet. Nothing was written under benchmarks/retry-policies/.

## Async code, timers, threads or streams

### Async concurrency control (`async-concurrency`)

- **Proposal:** Task "limited-concurrency-trivial-tasks". Input: 100,000 pre-built trivial async tasks, each resolving to a deterministic value derived from its index (e.g. i*2+1), with a concurrency limit of 10. Operation: run all tasks through the library with the limit and wait for all to settle. Result: the ordered array of values (or a count plus a sum plus first/last values). The check also asserts that peak in-flight tasks never exceeds 10, via a counter incremented and decremented inside each task. Measure CPU time and memory of the whole run, including the event-loop turns. JS packages: p-limit and p-map (map over the inputs), fastq (queue.push with a promise worker), async (mapLimit), @henrygd/queue, @std/async (pooledMap, JSR), @core/asyncutil. Builtin baseline: a hand-written worker-pool loop over Promise. Left out because they do a different job: p-locate (first match), run-parallel and asynckit (no cheap limit semantics), and the worker-process pools (jest-worker, poolifier), which are process or thread parallelism, not task limiting. Other languages, once the harness supports them: Python asyncio.Semaphore or anyio CapacityLimiter, Ruby concurrent-ruby fixed thread pool, Go errgroup.SetLimit from x/sync, Rust async-executor or a futures buffer_unordered. Compare these only if the harness can say what equal work means across them.
- **Needs:** An async-operation task kind in the harness. It would await a promise (JS), future (Rust), coroutine (Python), or goroutine/thread join (Go, Ruby) per operation, and time the whole run, including event-loop or scheduler turns. The loop startup has to be handled alike in every language. The verifier would receive the resolved result and an in-flight-peak counter. For the other languages, adapter support for async runners (Python asyncio, Ruby threads or Async, Go goroutines, Rust executors). An agreed rule for what counts as equal work across thread-based and event-loop-based runtimes.
- **Why not now:** The job is concurrency-limited execution of async tasks (p-limit, p-map, fastq, async, @henrygd/queue, @std/async pool). It cannot be a single synchronous call: the result only exists after a promise or event-loop turn. A sync-operation task cannot express that. A fair comparison also needs a design decision I'm not sure of. Rust, Python, Ruby and Go would use different primitives (executors, threads, tasks, goroutines), so deciding what equal work means across them is a harness-level call. The Rust and Go packages (rayon, threadpool, async-executor, x/sync) and the Python and Ruby ones (anyio, trio, concurrent-ruby) are also thread or event-loop based. The PyPI, RubyGems and Go module entries cannot be adapters of a synchronous task yet. Nothing was written under benchmarks/async-concurrency/.

### HTTP application servers (`http-application-servers`)

- **Proposal:** Start the server on a loopback port with a trivial application callback that returns a fixed 1 KB body. ### Image processing (`image-processing`)

### Child process execution (`process-execution`)

### Resource pools (`resource-pools`)

- **Proposal:** Start a local SSH/SFTP server in a fixed container or process, with a fixed key and a 100 MB fixture file. Measure CPU time and memory of the client process for two jobs. First, 1,000 short commands over one connection. Second, an SFTP upload and download of the 100 MB file, with a checksum verified outside the timed section. Packages: paramiko (Python); net-ssh, net-sftp and net-scp (Ruby); pkg/sftp with x/crypto/ssh (Go). Add npm ssh2 and ssh2-sftp-client, and crates such as russh and ssh2, if the brief is extended. Exclude sshtunnel, which is a tunnelling helper and not a command or transfer client.
- **Needs:** An async or network task kind with a managed local SSH server (setup and teardown, fixed host key and credentials, readiness check). Support for PyPI, RubyGems and Go module adapters in that kind. Child-process and long-lived-connection handling. A way to compare command output and file checksums outside the timed section. Isolating server CPU from the client's measurement.
- **Why not now:** An SSH/SFTP client needs a network connection to an SSH server, which cannot be a synchronous in-memory call. The brief lists only PyPI (paramiko, sshtunnel), RubyGems (net-ssh, net-scp, net-sftp) and Go (pkg/sftp) packages. No npm, JSR or crates.io packages are listed, and there is no standard-library SSH client. No adapter could be written. I wrote nothing under benchmarks/ssh-client.

### WebSocket messaging (`websocket-messaging`)

- **Proposal:** Measure a codec round trip, in memory, on about 100,000 mixed text and binary messages. A masked client frame is encoded, the server decodes it, the server replies with an unmasked frame, and the client decodes that. Include fragmentation and control frames (ping, pong, close). Then check that the decoded payloads equal the inputs. Candidates: - Sans-I/O: wsproto, websocket-driver (Ruby) and websockets' sans-I/O protocol layer (Python). - Go: gobwas/ws (wsutil), gorilla/websocket and nhooyr/websocket over net.Pipe or a buffer. - Rust: tungstenite over an in-memory Read/Write. - JavaScript: ws over a loopback socket (a second variant), or its Sender/Receiver with an explicit note about internal use. If the loopback variant is wanted, run it as an async or server task in a separate task kind.
- **Needs:** A task kind for async or loopback socket work with a long-lived server process, or a sync kind that supports in-memory duplex streams. Support for PyPI, RubyGems and Go module adapters in sync tasks. A decision on whether internal classes such as ws's Sender and Receiver count as fair adapters.
- **Why not now:** The brief's own idea is a loopback echo (network, async, long-lived sockets), which is not a sync-operation. The in-memory alternative has no shared public API. ws only documents sockets and servers, and its frame Sender and Receiver classes are internal modules, not a supported API. tungstenite can be driven over an in-memory stream in Rust. JavaScript has no standard-library WebSocket codec, and Python, Ruby and Go have none either. PyPI, RubyGems and Go packages cannot be sync adapters yet. That leaves at most ws and tungstenite as adapters, and ws would need undocumented internals, which is neither fair nor a plain default-usage case. Nothing was written under benchmarks/websocket-messaging/.

- **Proposal:** Measure generating a fixed multi-page PDF (about 100 pages of paragraphs plus a table) from fixed in-memory data. Packages: reportlab, fpdf2 and pydyf (PyPI), prawn with prawn-table (RubyGems), gofpdf (Go). A common way to verify binary PDF output across languages, such as a page-count and text-extraction check that does not run in the timed call. ### Reactive signals (`reactive-signals`)

- **Proposal:** Task "dependency-graph-updates", kind sync-operation. Build a fixed graph of about 50 source signals, about 200 derived (computed) values in a layered diamond and chain topology, and about 50 effects. Apply a deterministic series of source writes, some batched. Verify with the final values of all derived nodes plus a per-effect run count. Check that an effect is not run again when a value is unchanged and that diamond dependencies do not glitch, which would make glitch-free propagation the strict part of the check. Candidate packages: @patrickjs/signals (JSR), plus the main npm signals libraries that the brief omitted, such as @preact/signals-core, alien-signals, signal-polyfill, @maverick-js/signals, solid-js (reactive core only), @vue/reactivity, mobx and @angular/core signals. Add Rust crates only if some exist that can do this, for example futures-signals or leptos reactive_graph, after confirming they are synchronous. Ask first whether the taxonomy and brief should be widened to those npm packages. Their ranks may have been missed by categorization.
- **Needs:** No harness feature is missing. The decision needed is the package list: either re-run categorization so the real signals libraries are in the brief, or approve adding them by hand. The effect-run-count check also needs a shared definition of when effects are flushed, because libraries differ (synchronous, microtask or explicit flush). That is a design decision for an Opus pass.
- **Why not now:** The task itself would be synchronous (build a graph, set sources, read derived values and count effect runs). But the brief's packages do not offer a common operation. zustand is a framework-oriented store with no computed values or dependency tracking, and the brief puts that kind of store out of scope. @kling/react-store is also a React store. @libs/reactive is observable objects with no derived-value graph. @dnbkr/cygnals is unclear. Only @patrickjs/signals (a JSR TC39 signals polyfill with State, Computed and Watcher) is a real signals library, so at most one adapter fits. There is no standard-library builtin, and no Rust crate or other-registry package is listed. Fewer than two adapters can honestly do the same job, so I wrote nothing under benchmarks/reactive-signals/.

### Source map generation (`source-map-generation`)

- **Proposal:** Task "record-mappings". Each operation builds a source map in memory. The input is a deterministic list of about 100 source files with names and contents, plus several thousand mapping tuples (generated line/column, source index, original line/column, optional name index). The call adds every mapping through the builder API, then produces the version 3 map with its VLQ-encoded "mappings" string. The verifier compares version, sources, names and the exact mappings string across adapters. Participants: npm @jridgewell/gen-mapping (GenMapping, addMapping, toEncodedMap), the Rust crate sourcemap (SourceMapBuilder, into_sourcemap, to_writer or to_json), and possibly npm source-map (mozilla SourceMapGenerator) if the brief adds it. magic-string would go in a separate "edit-tracking" task, where it applies the same fixed edits to a string and generates a map, compared with other edit-tracking libraries. The builder's JSON string or object output would be mapped to the common shape in each language alike. Check whether the crate's builder dedupes sources and names the way gen-mapping does, so that the mappings strings are identical.
- **Needs:** A decision on whether the output is the encoded object or a JSON string. This matters because gen-mapping returns an object with no JSON.stringify step, while the crate serializes JSON. A second comparable library, either source-map on npm or a JSR equivalent. I did not confirm that the sourcemap crate can reproduce gen-mapping's exact encoded mappings, including the ordering and deduplication rules. If the schema permits, a way to compare only the sources/names/mappings fields.
- **Why not now:** The brief lists only two npm packages, and they do different jobs. @jridgewell/gen-mapping records explicit generated-to-original mappings and encodes them. magic-string tracks string edits and derives a map from them, so it cannot take the same input. A fair shared task needs a design decision I'm not sure of. There is also only one clear second implementation, the Rust sourcemap crate, and no standard-library builtin. The output shapes differ: gen-mapping's toEncodedMap returns an object, while the crate writes JSON. Mapping both to one common form without timing extra work for one side needs careful design.
