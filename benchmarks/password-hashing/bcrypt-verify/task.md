# bcrypt hash and verify

One operation takes three strings, a password and two candidates, and does
what a login system does: hash the password with bcrypt and a fresh random
salt, then check each candidate against the stored hash. So one operation is
three bcrypt runs, one of them a hash with salt generation. The result is two
booleans (does the first candidate match, does the second) and the hash that
was made. There are 36 fixtures, built deterministically: short and long
passwords, punctuation, accented and CJK text, emoji, spaces, and wrong
candidates that differ by one character, by case, by a leading character or by
a trailing space. Which candidate is the password changes from fixture to
fixture: the first only, the second only, neither, or both. Every string is at
most 72 bytes in UTF-8, the limit bcrypt reads, and none contains a NUL byte,
so all packages see the same effective input. The last fixture is exactly 72
bytes with the wrong candidate differing only in the final byte.

A correct output has the two expected booleans for that fixture, so a constant
answer fails, as does a package that accepts a wrong password, rejects the
right one or cannot verify its own hash. The returned hash must be a
60-character bcrypt string at cost 8 (`$2b$08$...`), with a salt that differs
in every fixture. The hash is not checked against an independent bcrypt
implementation. Returning it costs nothing: it is the string the package
already produced.

Cost is fixed to 8 for every package (bcrypt's default is usually 10 to 12).
Everything else is left at its default: the salt is generated by the package,
and the hash is the standard 60-character `$2b$08$...` string, which each
package produces and parses itself. Salt generation, hashing and both
verifications are inside the timed call. Nothing is cached between calls.

Accepted as equivalent: the minor version prefix of the hash (`$2a$`, `$2b$`,
`$2y$`), since all are the same algorithm for these inputs.

Only bcrypt is measured because scrypt and Argon2 have no cost setting equal to
bcrypt's. The `@felix/bcrypt` and `@da/bcrypt` JSR packages are left out: their
API is asynchronous (Deno FFI and a Web Worker per call respectively), which
this synchronous task cannot time. `@stdext/crypto` is left out too: its installed bcrypt `verify` returns true for any
password and hash, so it cannot pass the check. Bun's `Bun.password` is included as a
runtime built-in that runs on Bun only.
