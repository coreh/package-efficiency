# Parse and evaluate against 8 bindings

One operation takes an expression (a string) and 8 variable sets (objects of
eight float variables `a b c d x y z w`). It parses the expression once, inside
the call, and evaluates it against each of the 8 sets, returning the 8 results
in order. The parse is part of the call every time and nothing is kept between
calls (a library object built once at load, such as asteval's `Interpreter`, is
setup, not a cache of results).

The 40 expressions have 5 to 40 operators:

- 12 written by hand: precedence and associativity (`a - b - c`,
  `a - (b - c)`, chained division, `-a * b`, `-(a + b * 2.50)`), and comparisons;
- 28 generated by a seeded generator: `+ - * /`, unary minus, parentheses
  written only where precedence needs them, and `min(x, y)`, `max(x, y)`,
  `abs(x)`. Every division has a denominator of the form `abs(...) + 1.00`.
  Of these, about a third compare two arithmetic expressions with `<`, `<=`,
  `>` or `>=` at the root.

Every literal is written with a decimal point (`2.00`) and every variable is
a non-integral float, so no language reads a whole number. Variable sets are
chosen so that magnitudes stay below 1e4 and, for a comparison, so that the two
sides never differ by less than 0.1 percent and both outcomes occur among the 8.

## What counts as correct

The generator keeps the tree it wrote; the scenario evaluates that tree itself
in IEEE doubles. An output must be a list of 8 values:

- for an arithmetic expression, numbers within `1e-9 * max(1, |expected|)`;
- for a comparison, a boolean equal to the expected one, or the number 1 or 0
  for it (some libraries return 1.0 and 0.0). A boolean is not accepted for
  arithmetic.

The tolerance is there because Dentaku computes in `BigDecimal` and the others
in doubles; every entry that passes agrees with the reference far inside it.
The scenario asserts at load that a list of zeros, a list of `false`, and the
value of the first variable are all rejected.

Left out of the fixtures, because the libraries disagree: power (`^` or `**`),
`and`/`or`/`&&` spellings, `==`/`!=`/`=` spellings, integer division, modulo,
and the numeric value of a boolean inside arithmetic. Division by zero,
overflow and `NaN` are never produced.

## Packages

Each package is used the way its documentation shows, with default options.
The variables are handed over in the form the package takes; in Rust the
crate's own context or namespace type, built once per fixture outside the
timed call.

- `mathjs`: `compile(expr)`, `code.evaluate(scope)`
- `expr-eval`: `Parser.parse(expr)`, `evaluate(scope)`
- `filtrex`: `compileExpression(expr)`, then the function
- `evalexpr` (Rust): `build_operator_tree`, `eval_with_context`. Not passing: the
  crate has `math::abs`, not `abs`. The `evalexpr-abs-function` variant
  registers a custom `abs` in each context.
- `fasteval` (Rust): `Parser::parse`, `compile`, `eval` with a lookup closure.
- `meval` (Rust): Not passing: no comparison operators.
- `simpleeval` (PyPI): `SimpleEval(functions=...)`, parse, `eval(previously_parsed)`.
  The default function table has no `abs`, `min` or `max`, and a call to one
  raises `KeyError`; the entry passes the three Python built-ins, as the
  documentation shows for adding functions. There is no default-options entry,
  because it would crash instead of giving wrong values.
- `asteval` (PyPI): parse, `run(tree)` with the variables in the symbol table.
- `py-expression-eval` (PyPI): `Parser().parse(expr).evaluate(vars)`.
- `dentaku` (RubyGems): a new `Calculator` per call, `evaluate!(expr, vars)`. The
  calculator caches the parsed tree within the call, so the expression is parsed
  once; a calculator built per call keeps nothing between calls. Results are
  `BigDecimal`, converted by `describe` outside the timed call.
- `expr-lang/expr` (Go): `expr.Compile`, `expr.Run` with a map.

Not included:

- No standard-library adapter in any language: JavaScript `Function`/`eval`,
  Python `eval` and Ruby `eval` run arbitrary code, which is not what an
  expression evaluator is for, and Go has none.
- `jexl` (npm) has no `min`, `max` or `abs` without registering functions.
- `keisan` (gem): `max` takes one list argument, so `max(a, b)` raises.
- `govaluate`, `cel-go` (Go): no `abs`, `min`, `max` without writing the functions
  (cel-go only through an extension for the first two).
- `cexpr`, `cfg-expr` and `boolean.py` do other jobs.
- No JSR package does this job.

See [shared methodology](../../README.md) for timing and reproduction.
